- Eval results are gitignored by default; we'll commit chosen reports deliberately.

## Phase 1 — Dataset

**An eval is only as good as its answer key.** If the reference for dal is wrong, every score that touches dal is wrong — and nothing will warn me. That's why this phase is mostly human review, not code.

**Reference, not gold.** There is no single "true" calorie count for a katori of dal — it depends on the katori, the cook, the ghee. So each dish has a *reference* value plus a *tolerance band*. The band says how unsure we are about the right answer, not how lenient we're being: roti ±20% (homes agree), paneer butter masala ±35% (homes and restaurants don't).

**Recipe decomposition** — how we built references when IFCT only covers raw foods:
- Each dish is a recipe in **raw** grams: `1 katori toor dal = toor_dal:30; ghee:5; onion_tomato_masala:20`.
- Multiply each ingredient by its IFCT per-100g value, add them up → 151 kcal, 6.8g protein.
- Raw weights work because cooking mostly adds water, and water has zero calories. 30g of dry dal has the same calories whether it's cooked thick or thin.

**Inputs vs outputs.** I edit `ingredients.csv` and `dishes.csv`; `reference.csv` is generated by `build_reference.py`. Never hand-edit a generated file — the next run overwrites it. (Same idea as not editing a lockfile or a compiled bundle.)

**Pass/fail with a band — worked example.** Reference rajma = 189 kcal, band ±30% → pass range 132–246 kcal. Model says 240 → error = (240 − 189) / 189 = **27% → pass**. Model says 260 → 38% → fail.

**What the dataset deliberately tests:**
- *Single dishes* (15) — basic knowledge.
- *Quantity pairs* (roti 1/3, rice 1/2, idli 2/4) — does "3 roti" really give ~3× "1 roti"? A model can know roti well and still scale badly.
- *Messy inputs* (3) — how users actually type: "2 roti and thoda dal", "dal chawal" with no quantity.

**Weakest parts of the answer key** (be honest about these in any write-up):
- Katori size and oil amount are assumptions — oil is the biggest single source of disagreement.
- Paneer uses an NIN value, not yet checked against IFCT 2017.
- `onion_tomato_masala` and `mixed_vegetables` are rough approximations, but small shares of each dish.

**Side lesson — what you test decides what you catch.** The app's `lookup-nutrition` cache strips quantities ("4 roti" → key `roti`), so it may return 1 roti's calories for 4. Our eval calls the model directly, so it *cannot* see that bug — only an end-to-end eval through the real edge function could.

## Phase 2 — Runner

**Test what users actually get.** `prompts.py` copies the app's prompt verbatim (verified character-for-character against the edge function), with the same model, temperature (0.3) and JSON mode. An eval of a slightly different prompt measures something no user ever sees.

**Run and score are separate steps.** `run.py` only collects answers into `results/*.jsonl`; scoring comes later. Payoff seen immediately: I corrected IFCT values in `ingredients.csv` *after* the run — we just rebuilt the reference, no need to re-call the model.

**Why `.jsonl`** (one JSON object per line): each call is appended as it finishes, so a crash at call 50 keeps the first 49. Standard format for eval results.

**Why repeat each question 3×:** LLMs aren't deterministic, even at low temperature. One answer can be luck; three show whether it's a pattern.

**First findings from eyeballing run `20261014-131729` (gpt-4o-mini, app prompt):**
- **Quantity scaling is broken.** 1→3 roti gave 104→210 (2×, not 3×). 2→4 idli gave ~113→160 (1.4×, not 2×). 1→2 katori rice gave 130→~410 (3.2×, not 2×).
- **Consistent ≠ correct.** "3 roti = 210" came back identical all 3 times — confidently wrong.
- **Some dishes are unstable.** Paneer paratha + curd: 350 / 400 / 450. In the app, the cache freezes whichever answer came first for every user.
- **Protein is inflated on dal dishes.** Toor dal 10–12g vs reference 6.8g; dal chawal 18–20g vs 10.7g. For an app built around protein targets, this matters most.
- **Cost:** 63 calls = $0.0036 (≈ ₹0.30). Cost is not a reason to skip evals.

## Phase 3 — Scoring & report

**Baseline** (gpt-4o-mini, app prompt, run `20261014-131729`) — the "before" number:

| | Calories | Protein |
|---|---|---|
| Pass rate | **67%** | **68%** |
| Median error | 18% | 25% |
| Bias | −1% | +8% |

**Metrics, and what each one is for:**
- **Pass rate** — % of answers inside the band. The headline; easy to explain to anyone.
- **Median absolute error** — how big a typical miss is, ignoring direction. Median, not mean, so one wild answer doesn't dominate.
- **Bias** — median *signed* error: does it lean high or low?
- **By category** — the same metrics per slice. Overall numbers hide where the weakness is.
- **Consistency (spread)** — same question, how different are the answers?

**Averages hide errors.** Calorie bias is −1% — looks perfect. But median error is 18%: big over-estimates and big under-estimates cancel out. Always report error *size* and *direction* separately.

**Scoring decisions I made (and must disclose):**
- Protein passes inside the band **or** within ±2g — percentages are unfair on small numbers.
- A broken/missing answer counts as a **fail**, never silently skipped (skipping would inflate the score).
- Pass rates are per call; per-dish errors use the median of the repeats.

**Findings:**
1. **Quantity scaling is the weakest area** — 22% pass. 1→3 roti scaled 2× (should be 3×); 1→2 katori rice scaled 3.1× (should be 2×).
2. **Protein is inflated on every pulse dish** — dal chawal +87%, khichdi +79%, toor dal +76%, sambar +75%, rajma +49%, chole +37%. Rajma/chole *calories* are right (−1%), so it's not just a bigger-katori assumption: the model gives these dishes more protein per calorie than the recipe has. **Caveat:** check our own katori assumption (30g dry dal) before claiming the full gap — fixing the answer key is normal eval work.
3. **Consistent ≠ correct** — 11/21 dishes answered identically 3/3 times, including wrong ones.

**User impact:** someone eating dal + rajma + khichdi in a day may be told they had 10–15g more protein than they did — and believe they hit a target they missed.

## Phase 4 — Experiments

**Rule: change one thing at a time.** Same 21 dishes, same scoring, only the model *or* the prompt changes. (Exception, disclosed: Luna is a reasoning model and rejects `temperature`, so Luna runs change both model and sampling setting.)

**Results** (`results/comparison_20261014-192450.md`):

| Run | Cal pass | Protein pass | Quantity pass | $ / 1k lookups |
|---|---|---|---|---|
| gpt-4o-mini, app prompt (baseline) | 67% | 68% | 22% | 0.057 |
| gpt-4.1-mini | 68% | 68% | 67% | 0.155 |
| gpt-4.1 | 67% | **90%** | 0% | 0.774 |
| gpt-4o-mini, v2_decompose prompt | 59% | 52% | 33% | 0.188 |
| **gpt-5.6-luna, reasoning none** | **94%** | 71% | **100%** | 0.096 |
| gpt-5.6-luna, reasoning low | 89% | 78% | 100% | 0.130 |

**What I learned:**
1. **Measure, don't assume.** "Luna is cheaper and better" → actually ~1.7× the cost, but +27 pts on calories. Half the rumour was wrong.
2. **Bigger ≠ better.** gpt-4.1 costs 14× and scores the same on calories (it under-estimates, −18% bias) — but it's the best at protein. Models have different strengths.
3. **A prompt "fix" can make things worse overall.** v2 fixed exactly what it targeted (3 roti: 0/3 → 3/3) and broke upma, idli, rice and messy inputs. Testing only the dish I was trying to fix would have shipped a regression.
4. **Reasoning isn't free and didn't clearly help.** Luna low vs none: differences inside the noise band, 35% more cost. Hidden reasoning tokens are billed as output.
5. **Noise level:** with 21 dishes × 3, one dish ≈ 5 pts. Only trust differences above ~10 pts. Look at which dishes flipped, not just the headline.
6. **Data leakage is easy.** My first v2 prompt used "3 roti, 35g flour" as its example — a test question with its answer. Check every prompt for test data. The cleaner a score jump looks, the more suspicious to be.

**Not proven yet:**
- I chose the winner on the same 21 dishes I tested on → need a **held-out set** (new dishes, run once) before trusting it.
- Luna's price is from aggregators; confirm on OpenAI billing.
- Chole fails for *every* model → maybe our reference (35g dry chana) is the problem, not the models.
- Protein is still weak for everything except gpt-4.1.

**If switching the app to Luna:** remove `temperature` (Luna rejects it), add `reasoning_effort: "none"`, and fix cost logging in `ai-guard.ts` — it's hard-coded to gpt-4o-mini rates and would silently log wrong costs.

## Part B — Grounding (protein)

**Idea:** split the job. Model estimates WHAT and HOW MUCH (raw grams, names restricted to `ingredients.csv` by a strict JSON schema); code supplies the nutrition facts (IFCT) and the arithmetic. Prompt `v3_grounded`, function `ground()` in `run.py`.

**Result** (Luna, reasoning none, run `20261015-000622`):

| | Cal pass | Protein pass | Bias (cal) |
|---|---|---|---|
| Luna, app prompt | **94%** | **71%** | +11% |
| Luna, grounded | 56% | 57% | +28% |

**Why — the portion diagnosis** (`score.py` section, only for grounded runs). IFCT supplies facts on both sides, so every gap is portion size. Luna's raw grams vs ours: toor dal 1.75×, moong 1.67×, urad 1.50×, chana 1.43×, rice in mixed dishes 1.33×; simple foods matched (rice 50g, curd 150g).

**Lessons:**
1. **Grounding moves the guess; it doesn't remove it.** The model still estimates grams — and it's *worse* at raw-gram recipes than at recalling dish-level numbers ("1 katori dal ≈ 150–180 kcal" is everywhere online; raw-gram decompositions aren't).
2. **A plausible architecture can lose.** "Model for language, code for facts" is good design in general — here it measured 38 points worse. Without the eval this would have shipped as an "improvement".
3. **I drew a conclusion from 5 calls and the full run reversed it.** Smoke tests check plumbing, not results.
4. **Scorers have bugs too.** First version of the diagnosis flagged "ghee left out" when Luna used oil — nutritionally identical. Fixed by comparing ghee/oil as one.
5. **Structured outputs:** a strict JSON schema with an enum guarantees valid ingredient names (no matching step needed). Fuzzy/vector matching only earns its place with hundreds of foods and free-text names.
6. **The eval shares a source with the answer key** (both use `ingredients.csv`), so it measures only gram estimation and cannot catch a wrong IFCT value. Fine to accept — must be disclosed.

**Open question — who's right about portions?** Our 30g dry dal per katori vs Luna's 35–45g. Settle it with a kitchen scale, not more model runs.

**Decision:** don't ship grounding. Luna + app prompt stays the winner; protein stays at 71% until better portion data exists (measurement, or user corrections from the photo sheet).
